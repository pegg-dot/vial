VIAL · Deep-dive audit · 21 Jul 2026 · 6 parallel auditors

What's not done, not self-serve,
or doesn't add up — the honest list.

Six read-only agents went through self-serve, the buyer journey, frontend/UI, backend completeness, real/demo coherence, and the operator side — reading code and probing the running app with the real BPC-157 data live. This is the deduplicated, prioritized result. The good news: the core machinery is genuinely well-built. The issues cluster into five themes.

The one-line verdict

The buyer research experience works well for an anonymous guest, and the provenance/evidence/lab machinery underneath is real and strong. But the product is not launch-ready and not self-serve: nobody can create an account, the real data we just added makes real vendors look less trustworthy than the fake ones, an entire abandoned Stripe marketplace contradicts the affiliate model, and several headline surfaces silently show only demo data on a real deploy. 5 P0 themes, ~16 P1s, ~11 P2s. None are fatal; all are fixable.

The five blockers

P0 — these break the mission or the launch

P0 · 1

The real data makes real vendors look like the scams

The single most important finding, because it inverts the entire "don't get scammed" purpose. On /compounds/bpc-157, the real Eternal Peptides ($34.99, cheapest, actually real) shows an empty evidence matrix, "★ 0 (0)" rating, "0% tests current," and "Open risk flags: 2" — while the fictional Northstar shows a full evidence matrix and "★ 4.8 (184)." The app steers buyers toward the fabricated vendors. Four compounding causes: the product-detail hero renders the 0-rating unconditionally (the card was already fixed, the detail page wasn't); the evidence matrix has no empty state so it's a blank white box; the reputation "risk flags" dimension counts benign Curator opportunity signals as "risk signals and fraud cases" and pins "2 open flags" on real companies; and freshly-ingested vendors read as "0% documented" (status established) instead of "unknown."

products/[slug]/page.tsx:99 · evidence-matrix.tsx:7 · reputation/repository.ts:106-119 (+ label-key bug: open_risk_flags vs risk_flags) · reputation/repository.ts:60-69
P0 · 2

Nobody can create an account — for any role

There is no signup anywhere — no /register, no create-account API, no "create account" link on the login page. The only accounts are 5 hardcoded demo users, seeded only when NODE_ENV!=="production". On a real prod deploy there are zero accounts and no way to make one. Every durable feature (account, saved searches, alerts, For-You) is unreachable by a real person. Vendor and lab "self-serve onboarding" are demo skins over single seeded tenants — an invited teammate gets no credentials and still can't log in. And adding a real vendor/source needs an engineer running a script with an env flag; no UI, even admin, can do it. The aggregator cannot aggregate a new vendor, and no user can become a user, without an engineer.

auth/foundation-seed.ts (only accounts) · login/page.tsx (no signup) · seller/layout.tsx:7-9 · lab/layout.tsx:5 · scripts/ingest-real-bpc157.mjs (script-only)
P0 · 3

An abandoned Stripe marketplace contradicts the whole affiliate pivot

VIAL ships a complete, wired, seeded transactional marketplace — cart → checkout → orders → settlements → payouts → disputes → underwriting → returns → fulfillment — that directly contradicts "VIAL never sells anything." It's ~33% of the admin surface, most of the seller experience (payments, payouts, chargeback evidence — all meaningless under affiliate-out), and a live-but-orphaned checkout you can still reach by URL even though the product copy swears it doesn't exist. The cart provider even fires /api/v1/commerce/cart on every authenticated page load for this dead feature. Money is safely gated, but it's a large contradiction, maintenance burden, and trust hazard. Needs an explicit decision: delete, quarantine as "legacy," or revive.

app/checkout · app/cart · commerce-cart-provider.tsx:44,52 · seller-shell nav (payments/payouts/disputes) · ~15 of 43 admin pages
P0 · 4

Headline surfaces silently show only demo data on a real deploy

Three independent runtime gaps mean the real data can't actually flow through the product's advertised surfaces: (a) No runtime path to real evidence — batch passports are seed-only, so the live vendors can never get a real lab passport; the flagship "How we check" trust surface is permanently the one fictional Aperture demo. (b) No reliable scheduler — refresh + signals fire only from one Vercel cron; the checked-in docker-compose.yml has none, plus a CRON_SECRET footgun that 401s legit callers — so live prices go stale and signals freeze (the 5 signals showing are a stale one-off from a manual click). (c) Live entities never enter the registry — the public "citeable IDs" API resolves only demo data and excludes 100% of the real data.

evidence-network/repository.ts:152 (seed-only) · api/internal/cron/refresh/route.ts:8-17 · docker-compose.yml · registry projects from canonical_entities at seed only; live ingest never mints IDs
P0 · 5

Wrong "observed" market numbers on real data from the ingest

The publication cascade recomputes a compound's listing count, median, and doc-coverage on publish — but not price_change. So BPC-157 correctly recomputed to 6 listings / $46 median / 33% docs, but still renders the seeded "−4.8%" as a live "observed" trend (the real median actually dropped ~11.5% when the live vendors landed). It shows on the compound header and animates in the home ticker. Any future price-driven compound shows a stale trend forever. (Also: the home "Median price" tile is actually computing the mean.)

intelligence/cascade.ts:112-114 (price_change missing from recompute) · compounds/[slug]/page.tsx:62-64 · page.tsx:61,74

What's genuinely good

Search

Fuzzy, typo-tolerant, and it finds the live vendors — "etarnal" still surfaces Eternal first.

/how-we-check

Genuinely delivers the trust promise — evidence ladder, six-question COA breakdown, "unknown stays visible." Substance, not words.

/passports

The best surface in the app: decomposed confidence, and it preserves conflicting lab results instead of averaging them.

The lab subsystem

Deep and coherent with the pivot — hash-chained custody, real report issue/revoke, a real runtime path from lab report to buyer passport.

Provenance machinery

snapshot → claim → review → publish → cascade is well-built and internally consistent. The bones are right.

Reputation honesty

For live vendors it returns honest per-dimension "unknown" (aside from the risk-flags + 0%-docs bugs in P0-1).

Guest research flow

Browse, search, compare, and a local watchlist all work with no login — the right part to be strong.

Safety interlocks

MCP tools are proposal-only; commerce is triple-gated; the affiliate CTA stays inert. Security posture is sound.

What I'd fix, in order

Grouped so each phase is a coherent, shippable unit. Nothing here is started — this is an audit.

  1. Kill the trust inversion + the embarrassing leaks (P0-1, the "Nate" leak, the "fictional" copy, "Awaiting first check"). Mostly display logic already solved in ProductCard — branch the detail page the same way, give the evidence matrix an honest empty state, fix the risk-flags dimension, and finish the labeling sweep into meta/FAQ. Highest impact, lowest effort, and it stops actively hurting real vendors.
  2. Make the real data cohere (P0-5). Add price_change to the cascade recompute and advance the evidence label off "Awaiting first check" on first publish; fix the median-vs-mean tile.
  3. Decide the commerce question (P0-3). One call — delete, quarantine as "legacy/simulation," or revive — then make the operator/seller surfaces consistent with it. This unblocks a lot of coherence.
  4. Close the real-data runtime edges (P0-4). A runtime path to real evidence, a scheduler that actually runs, and registry IDs for live entities — or scope those surfaces down until they exist.
  5. Answer the self-serve question (P0-2). This is a product decision as much as code: is launch buyer-only (guest research + affiliate-out, no accounts needed), or do accounts/vendor-onboarding come first? That decision reframes half of these findings.
  6. Then the frontend polish (P1/P2): wire or retire the orphaned pages, add loading/error states, real imagery, and consolidate the design tokens.

My recommendation: do phase 1 immediately (it's cheap and it's actively misleading buyers right now), then bring me the commerce and self-serve decisions — those two reframe everything else.
